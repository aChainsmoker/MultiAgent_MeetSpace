# DEV-007 — S3-хранилище аватаров и фотографий комнат

Статус: Запланировано

## Цель

Подготовить S3-совместимый адаптер хранения изображений в Infrastructure через AWSSDK.S3. Поддержать аватары пользователей и фотографии переговорных. MinIO/S3 сейчас не разворачивать и не подключать; поведение SDK в тестах полностью мокается.

## Источники

- `AGENTS.md`, `goal.md` и актуальный код проекта.
- Существующие `Infrastructure/Options/S3Options.cs` и регистрация в `Api/Extensions/OptionsServiceCollectionExtensions.cs`.
- `User.ProfilePhotoKey`, `User.SetProfilePhotoKey`, `Room.PhotoKey`, `Room.SetPhotoKey`.
- EF mapping: `ProfilePhotoKey` и `PhotoKey` уже имеют максимальную длину 500.

## Исходное состояние по предоставленному коду

- `S3Options` содержит только `BucketName` и `PresignedUrlLifetimeMinutes`.
- Для S3 уже настроены binding и ValidateOnStart через AddMeetSpaceOptions.
- По goal.md бакет — `meet-space`, срок GET-ссылки — 60 минут.
- В предоставленном коде нет файлового контракта Application, S3-адаптера и полного сценария сохранения фото через репозитории. Не считать их существующими без проверки актуального репозитория.
- В приложении уже используются ключи объектов, а не URL: сохранить эту модель. Миграция БД для базовой интеграции хранения не требуется.

## Что сделать

### 1. Архитектура

Подготовить краткий документ `docs/architecture/DEV-007-s3-image-storage.md`:

- Проверить актуальные проекты, package references, соглашения DI и тесты. В предоставленном текстовом срезе csproj и тесты отсутствуют, поэтому версии SDK/пакетов сверить с настоящим репозиторием.
- Определить небольшой контракт Application, например `IImageStorage`, и реализацию `S3ImageStorage` в Infrastructure. Не возвращать AWS-типы наружу.
- Предусмотреть загрузку изображения из Stream с категорией (аватар/фото комнаты), идентификатором владельца ресурса и ContentType; результат — сгенерированный object key.
- Предусмотреть удаление по ключу и получение временной GET-ссылки по ключу. Поток скачивания, публичные URL, multipart upload и presigned upload в этот тикет не входят.
- Application не зависит от AWSSDK.S3, MinIO SDK, IFormFile, HttpContext и реализаций Infrastructure. Infrastructure реализует контракт Application и зависит от IAmazonS3 через DI.
- Владелец ресурса в параметрах адаптера служит для формирования ключа, а не для аутентификации. Проверка пользователя/роли и запись ключа в сущность — отдельные Application-сценарии.
- Зафиксировать владение Stream, поддержку seek/non-seek потоков, валидацию входа, отображение ошибок и поведение отмены.

### 2. Контракт хранения и ключи

- Использовать разные префиксы, например `avatars/{userId}/{uniqueId}.jpg` и `rooms/{roomId}/{uniqueId}.jpg`.
- На каждую загрузку генерировать новый уникальный ключ. Не использовать исходное имя файла, email, пароль или произвольный путь пользователя в качестве ключа.
- Ключ должен укладываться в существующий лимит 500 символов. Расширение, если используется, выводить из согласованного ContentType.
- Сохранять в БД в будущем только ключ; временную ссылку не хранить в сущности и не выдавать за постоянный адрес.
- Использовать один настроенный приватный бакет. Не устанавливать public-read ACL и не создавать/перенастраивать бакет автоматически.
- Для аватаров и фото комнат использовать общую реализацию, не дублировать S3-код в двух сервисах.
- Старое фото не удалять автоматически при загрузке нового: адаптер не знает, успешно ли будущий Application-сценарий сохранит новый ключ в БД. Удаление старого объекта и компенсация при ошибке БД относятся к следующему тикету сценариев фото.

### 3. Конфигурация и регистрация

- Расширить существующий S3Options, не создавать параллельную секцию с теми же настройками.
- Предусмотреть endpoint для MinIO, регион подписи и ForcePathStyle для S3-совместимого сервера. Сохранить BucketName и PresignedUrlLifetimeMinutes.
- Сохранить значения `meet-space` и 60 минут по умолчанию в appsettings, а не дублировать их в адаптере.
- Настроить credentials через окружение/локальные секреты. В tracked appsettings/примерах допустимы только имена параметров и заглушки, без настоящих ключей.
- Для будущего локального MinIO учитывать, что endpoint в подписанной ссылке должен быть доступен будущему клиенту. Не заменять host в уже подписанной ссылке строковыми операциями.
- Сохранить существующий extension-метод binding/валидации Options. Добавить компактный метод DI для Infrastructure/S3 и минимальный вызов из composition root при необходимости.
- Регистрация и сборка приложения не выполняют S3-запросов, проверку бакета, получение metadata credentials или создание ресурсов.
- Определить явный режим отключения S3 до настройки, например `S3:Enabled=false`; при включении проверять необходимые параметры. В отключённом режиме приложение сохраняет возможность запуска, а хранилище не должно имитировать успешную загрузку/удаление.
- Не включать S3 по умолчанию и не требовать настоящие credentials для существующих тестов и /health.
- Описать настройки и будущий запуск в README. Docker Compose для MinIO и запуск контейнеров в этот тикет не входят.

### 4. Реализация S3-адаптера

- Использовать AWSSDK.S3 и инъекцию IAmazonS3; SDK-клиент не создавать внутри каждой операции.
- Реализовать PutObjectAsync для загрузки с правильными BucketName, Key, InputStream и ContentType.
- Реализовать DeleteObjectAsync по ключу. Удаление отсутствующего объекта считать идемпотентным согласно контракту S3; не маскировать другие ошибки как успешное удаление.
- Реализовать получение подписанной GET-ссылки с TTL из Options. Генерация ссылки не должна предварительно проверять существование объекта; ссылка сама по себе не доказывает наличие объекта.
- Использовать методы подписи, доступные в фактической версии SDK. Если выбранный метод не поддерживает CancellationToken, не придумывать передачу токена в несуществующий overload; описать ограничение и проверять отмену до вызова.
- Время истечения вычислять в UTC; для тестов предусмотреть управляемый источник времени, не менять существующий бизнес-контракт локального времени бронирований ради S3.
- Передавать CancellationToken в операции SDK, поддерживающие его. OperationCanceledException не преобразовывать в ошибку хранилища.
- Не возвращать key как результат успешной загрузки после ошибки SDK.
- AWS-исключения за границей Infrastructure переводить в понятную ошибку контракта хранения с сохранением inner exception; не оборачивать программные ошибки и отмену без разбора.
- Не логировать credentials, байты файла и полную подписанную ссылку.
- Входной Stream принадлежит вызывающему коду и не должен закрываться адаптером/SDK. Учесть соответствующие настройки PutObjectRequest; IAmazonS3 из DI также не Dispose-ить в каждой операции.
- Перед обращением к SDK отвергать null/нечитаемый/пустой поток, неверную категорию/пустой ID ресурса, неподдерживаемый ContentType и пустой/посторонний ключ. Поддерживаемые форматы и ограничения размера определить в архитектурном документе, числовые лимиты не придумывать молча — при отсутствии требований уточнить у владельца.
- Если вводится лимит размера, проверять фактические данные/доступную длину потока, не доверять только переданному размеру. Поведение non-seek потоков определить явно.
- Проверка ContentType сама по себе не доказывает, что байты являются изображением: обозначить границу проверки и не заявлять полноценную проверку содержимого без реализации. Декодирование, ресайз, антивирус и очистка метаданных не добавлять впрок.

## Тестирование

- Использовать существующий xUnit и библиотеку моков проекта; мокать IAmazonS3, а не сам проверяемый S3ImageStorage.
- Не использовать настоящий AWS-клиент для операций, реальные ключи, HTTP-сервер, S3, MinIO, Docker или БД. Моки должны обнаруживать неожиданные вызовы, а не возвращать успех на всё.
- Upload: правильный бакет, категория/префикс и ID ресурса, уникальный ключ <= 500, ContentType, исходный Stream, переданный CancellationToken и результат только после успеха.
- Проверить загрузку для обоих видов фото и отсутствие коллизии ключей при повторной загрузке одного ресурса. Не привязывать тест к конкретному случайному GUID.
- Проверить некорректные входные данные и отсутствие вызова SDK при отказе валидации. При лимите размера проверить границы и non-seek политику.
- Delete: правильный бакет/ключ/токен, согласованная идемпотентность, отказ на пустом/недопустимом ключе, корректная обработка ошибки SDK.
- Presigned GET: правильный ключ/бакет, HTTP-метод GET, срок относительно фиксированного UTC-времени и передача URL, возвращённого моком. Проверить отсутствие лишних Head/Get/List-запросов.
- Проверить отображение ошибок SDK, сохранение причины, распространение отмены и отсутствие ложного успешного результата.
- Проверить, что Stream не закрывается, и настройку запроса, запрещающую SDK закрыть его. Успех мока не доказывает поведения реального SDK — проверить оба аспекта отдельно.
- Проверить DI без сети и S3-конфигурацию: отключённый режим не требует настоящего сервера, включённый режим с невалидными параметрами выдаёт понятную ошибку без раскрытия секретов. При создании реального объекта клиента для проверки конфигурации использовать синтетические credentials и не выполнять операции/credential discovery.
- Выполнить существующие тесты, особенно Options/DI, и новые тесты адаптера. Не ослаблять старые проверки ради новых параметров.
- Независимый тестировщик записывает команды, exit codes, число обнаруженных/успешных/неуспешных/пропущенных тестов. Ноль тестов — не успешный прогон.
- Отдельно указать: совместимость с реальным MinIO, credentials, подпись/доступность ссылок, содержимое бакета и сетевые ошибки реально не проверялись. Для этого потребуется последующий интеграционный запуск.

## Границы

- Создать контракт Application, реализацию Infrastructure, необходимые Options/DI, документацию и тесты.
- Не реализовывать HTTP upload endpoints, frontend, изменение профиля/комнаты через репозитории, новые репозитории пользователей, миграции и сохранение ключей в БД.
- Правило «аватар — своего пользователя; фото комнаты — только менеджером» сохранить как требование к будущим Application-сценариям. Не помещать проверку ролей в низкоуровневый S3-адаптер и не объявлять её реализованной этим тикетом.
- Не менять Domain-сущности и их существующие поля ключей без обоснованной необходимости.
- Не запускать MinIO/AWS/Docker и не выполнять сетевые S3-запросы. Не создавать бакет и реальные credentials.
- Не выполнять push, создание PR и комментарии удалённо без отдельного указания владельца. При разрешении допускается отдельный локальный коммит.

## Критерии готовности

- Есть архитектурный документ с контрактом, границами и решениями по потокам, входным данным, ошибкам и отключению S3.
- Адаптер Infrastructure реализует загрузку обоих видов изображений, удаление и временные GET-ссылки через IAmazonS3.
- Domain/Application не зависят от AWS/MinIO SDK или HTTP-типов.
- Используются существующие поля object key и S3Options; нет URL в сущностях и дублирующих настроек.
- Регистрация не обращается к сети и не ломает запуск приложения без MinIO.
- Поведение адаптера проверено моками IAmazonS3; сборка и существующие тесты проверены.
- Отчёты содержат результаты и явное отсутствие реальной S3/MinIO-проверки.
- Статус «На проверке» после успешной проверки; «Завершено» устанавливает владелец.
