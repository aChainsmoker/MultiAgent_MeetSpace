# DEV-006 — DataAccess для PostgreSQL и тесты SQLite в памяти

Статус: На проверке

## Цель

Реализовать взаимодействие с БД через EF Core и Npgsql, опираясь на Domain и существующие интерфейсы Application после DEV-005. Подготовить Docker Compose для будущего запуска PostgreSQL. Сейчас контейнеры и PostgreSQL не запускать; проверять код на SQLite in-memory.

## Источники

- `AGENTS.md`, `goal.md`.
- Актуальные Domain, Application и результаты исправления ревью DEV-005.
- Существующие Options, архитектура и тесты.

## Что сделать

### 1. Архитектура

Результат: `docs/architecture/DEV-006-data-access-postgresql.md`.

- Изучить фактические интерфейсы репозиториев и их семантику: когда сохраняются изменения, как передаются CancellationToken и исключаемый BookingId, как сообщается конфликт записи.
- Спроектировать DbContext, конфигурации сущностей, репозитории, регистрацию DI и начальную миграцию PostgreSQL. Не изобретать новые несовместимые контракты без обоснования.
- Application и Domain не зависят от EF Core, Npgsql или DataAccess. DataAccess реализует интерфейсы Application и использует сущности Domain.
- Определить срок жизни DbContext и репозиториев, границы сохранения и транзакций. Не вводить универсальный Repository/UoW только ради шаблона.
- Описать отдельную тестовую конфигурацию SQLite in-memory и ограничения переносимости. PostgreSQL остаётся единственным production-провайдером.

### 2. Модель хранения

- Создать или дополнить проект `Backend/src/MeetSpace.DataAccess` по существующему соглашению.
- Добавить DbContext и Fluent API mapping всех существующих сущностей: пользователь, комната, оборудование, бронирование, refresh-токен.
- Настроить ключи, обязательность, длины столбцов, связи, таблицу связи комнат/оборудования, индексы и обоснованные правила удаления. Учесть приватные setters и доменные способы создания объектов.
- Не хранить пароль открытым текстом. Сохранить принятую Domain/Application модель password hash и refresh-токена; не создавать заново правила авторизации.
- Хранить дату/время бронирования без таймзоны согласно goal.md и выбранным в Domain типам. Не вводить неявную конвертацию в UTC.
- Согласовать длины столбцов с решением DEV-003: runtime-настройки валидации не должны незаметно менять EF-модель/схему.
- Подготовить начальную миграцию и model snapshot для Npgsql. Миграцию можно сгенерировать локально без подключения к серверу; к БД её не применять.
- При необходимости добавить design-time factory, не выполняющую сетевые подключения.

### 3. Реализации репозиториев

- Реализовать все существующие методы IBookingRepository и IRoomRepository в соответствии с актуальными контрактами.
- Реальные запросы и запись — через EF Core; не подменять production-хранилище коллекциями или SQLite.
- Передавать CancellationToken в асинхронные операции.
- Выполнять фильтрацию в БД, не загружать всю таблицу для последующей обработки.
- Для пересечений соблюдать принятые интервалы [начало, конец), комнату, дату и исключение только текущего BookingId при Update.
- Обеспечить получение данных пользователя и комнаты, необходимых DTO Application, без N+1 и без зависимости от lazy loading. Описать контракт загрузки навигаций или проекций.
- Для запросов без изменения использовать AsNoTracking там, где это соответствует контракту. Для обновления/удаления явно определить работу с tracked/detached сущностями.
- Не подавлять ошибки БД и не превращать все ошибки хранения в конфликт бронирования.
- Добавить PostgreSQL-защиту от конкурентных пересекающихся броней: предпочтительно ограничение БД либо обоснованный транзакционный механизм. Простая проверка перед Insert/Update недостаточна.
- Если используется provider-specific constraint, добавить его в миграцию и переводить только его распознанное нарушение в согласованную ошибку конфликта. Не трактовать любое нарушение FK/unique как конфликт времени.
- Указать, что PostgreSQL-специфичная гарантия пока не проверена запуском; не выдавать SQLite-тесты за подтверждение отсутствия гонки PostgreSQL.

### 4. Конфигурация и Docker Compose

- Добавить extension-метод регистрации DataAccess/репозиториев. Сохранить Program.cs компактным и существующий способ регистрации Options.
- Для production-конфигурации использовать Npgsql и строку подключения из конфигурации/окружения, не из захардкоженной строки с секретами.
- Подготовить Docker Compose только для PostgreSQL: конкретная версия образа без latest, named volume, healthcheck, настраиваемый локальный порт и параметры через переменные окружения.
- Добавить безопасный `.env.example` или дополнить существующий без потери других параметров. Настоящий `.env` не читать без необходимости и не коммитить.
- В README описать будущий ручной запуск контейнера, применение миграций, строки подключения с хоста и из контейнерной сети. Команды только записать, не выполнять.
- Подготовка DI не должна запускать БД или применение миграций. Не добавлять обязательное подключение к PostgreSQL при текущем запуске API. Автоматическое применение миграций и сидинг из goal.md явно оставить для отдельного этапа подключения/развёртывания.

## Тесты и проверка

- Использовать xUnit и SQLite in-memory (`Microsoft.EntityFrameworkCore.Sqlite`) вместо EF Core InMemory.
- Тестировать настоящие репозитории и DbContext, без mock DbSet и без mock репозитория, который проверяется.
- Для каждого теста создавать изолированную БД. Держать SQLiteConnection открытой до завершения теста; освобождать её после проверки.
- Создавать схему тестовой БД через EnsureCreated. Не применять Npgsql-миграции к SQLite.
- Использовать ту же общую модель/репозитории, что в production. Только неизбежные provider-specific различия локализовать и задокументировать; не менять смысл production-запросов ради прохождения SQLite-тестов.
- Не отключать FK и реляционные ограничения ради зелёных тестов. Не считать SQLite доказательством соблюдения PostgreSQL-типов, ограничений длины строк, collation, миграций или exclusion constraints.
- Проверить каждый метод существующих репозиториев: создание, получение, изменение, удаление, отсутствующие записи, выборки пользователя и календарного диапазона.
- Проверить пересечения (полное/частичное/вложенное/одинаковое), соседние интервалы, другую дату/комнату, исключение текущей брони и наличие другой конфликтующей брони.
- Подтвердить сохранение данных: после записи читать их через новый DbContext на той же открытой SQLiteConnection, а не только проверять tracked-объект.
- Проверить связи и загрузку необходимых навигаций на данных с несколькими пользователями/комнатами; не полагаться на случайно заполненный ChangeTracker.
- Добавить несколько проверок связки настоящего BookingService с настоящими репозиториями на SQLite: успешное бронирование, конфликт, изменение комнаты и удаление. Подменять только текущего пользователя, время и прочие внешние зависимости.
- Выполнить существующие Application/Domain/Options-тесты и новые DataAccess-тесты.
- Для PostgreSQL-only частей выполнить доступную проверку кода/миграции и сформировать отдельный список будущих интеграционных проверок: миграция с нуля, конкурентные Create/Update, перевод ошибок, откат транзакций. Сейчас не запускать эти сценарии на PostgreSQL и не отмечать их пройденными.
- Независимый тестировщик записывает команды, exit codes, количество успешных/неуспешных/пропущенных тестов. Ноль обнаруженных тестов — не успех. Ошибку трансляции запроса в SQLite не обходить переходом на ToList/AsEnumerable до фильтрации; сначала разобраться и описать различие провайдеров.

## Границы и запреты

- Не выполнять docker run, docker compose up, docker pull, запуск PostgreSQL, Testcontainers и развёртывание приложения.
- Не подключаться к существующей локальной/удалённой PostgreSQL и не применять миграции к реальной БД.
- Не реализовывать HTTP API, frontend, S3, JWT и прочую Infrastructure.
- Не создавать сидинг менеджера, комнат и демонстрационных броней в этом тикете; необходимость из goal.md сохранить в списке следующих задач.
- Взаимодействие с Git remote/GitHub запрещено: не делать fetch, pull, push, PR, комментарии и вызовы GitHub MCP. Допустим только локальный Git и локальный коммит. Получение NuGet-пакетов для сборки и чтение документации не являются публикацией и допустимы.
- Не изменять существующие локальные конфиги OpenCode и посторонние файлы.

## Критерии готовности

- Есть архитектурный документ и реализации существующих репозиториев в DataAccess.
- DbContext и mapping соответствуют Domain и согласованной схеме PostgreSQL.
- Подготовлены Npgsql-миграция, DI-регистрация, Compose и инструкция будущего запуска.
- Приложение и тесты не требуют сейчас работающего PostgreSQL.
- Репозитории и несколько связных сценариев BookingService проверены на SQLite in-memory, существующие тесты не регрессировали.
- PostgreSQL-only ограничения и непроверенные сценарии перечислены отдельно; нет заявления о полной проверке PostgreSQL.
- Отчёты заполнены; статус «На проверке». «Завершено» устанавливает владелец.
- Создан локальный коммит только изменений DEV-006; публикации и подключения к реальной БД не выполнялись.
